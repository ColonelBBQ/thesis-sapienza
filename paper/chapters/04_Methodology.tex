\chapter{Methodology}

This chapter describes the three components of the experimental pipeline: the BERT-based classifier that serves as the primary model under test, the LLM-based disambiguation procedure used to produce clarified variants of ambiguous sentences, and the LLM direct classification setup—spanning two models in both zero-shot and few-shot configurations—evaluated as an alternative to BERT. The chapter closes with the full experimental design, defining the dataset subsets and model configurations on which each component is evaluated.

\section{BERT Classification Pipeline}

The classifier follows the architecture and configuration established by the AI-CRAS framework~\cite{casalicchio2024aicras}, adopted unchanged to ensure direct comparability of results.

\subsection{Model Architecture}

The model is built on BERT\textsubscript{BASE-UNCASED}~\cite{devlin2019bert}, a 12-layer transformer encoder with 768-dimensional hidden representations and 12 attention heads, pre-trained on English text with a vocabulary of 30,522 WordPiece tokens. The pre-trained encoder is augmented with two task-specific layers: a dropout layer with rate 0.3 for regularisation, and a linear layer that maps the pooled 768-dimensional output of the \texttt{[CLS]} token to six logits, one for each cloud service category. The six categories are treated as independent binary classification targets (multi-label), so the model can assign zero, one, or several labels to any given sentence.

The loss function is binary cross-entropy with logits (\texttt{BCEWithLogitsLoss}), which combines a sigmoid activation with binary cross-entropy in a numerically stable single operation. Training uses the Adam optimiser with a learning rate of $3\times10^{-5}$ and weight decay of $10^{-6}$. No learning rate scheduling is applied.

\subsection{Preprocessing, Training, and Inference}

\textbf{Tokenization.} Input sentences are tokenised using the BERT WordPiece tokenizer in its uncased variant, converting all text to lowercase. Each sentence is padded or truncated to a fixed length of 300 tokens—the same limit used in AI-CRAS, sufficient to cover the longest sentences in the dataset. Special tokens \texttt{[CLS]} and \texttt{[SEP]} are prepended and appended respectively, and an attention mask distinguishes real tokens from padding.

\textbf{Training.} The dataset is split into training (85\%) and validation (15\%) partitions using stratified random sampling with seed 42, following the AI-CRAS protocol. Training proceeds for a maximum of 5 epochs with a batch size of 16, using full-batch validation after each epoch. An early stopping mechanism halts training if validation loss does not decrease between consecutive epochs, and the model checkpoint with the lowest validation loss is retained for evaluation.

All experiments are run on an NVIDIA T4 GPU through Google Colaboratory, with PyTorch as the deep learning framework.

\textbf{Inference.} At inference time, the model outputs six logits per sentence, which are passed through a sigmoid function to obtain probabilities in $[0, 1]$. A sentence is considered to carry a given label if the corresponding probability exceeds the threshold of $0.20$, the value used by AI-CRAS. This threshold was chosen in the original work to maximise recall without an excessive cost in precision, and is preserved here for consistency.

\subsection{Evaluation Metrics}

All evaluation follows the protocol established in AI-CRAS~\cite{casalicchio2024aicras}. For the binary task (requirement \textit{vs.} non-requirement), a sentence is classified as a requirement if it receives at least one label above the threshold. For the multi-label task, each of the six categories is treated as an independent binary problem. In both cases, the following standard metrics are reported, where true positives (TP), false positives (FP), and false negatives (FN) are defined per class or per category:

\begin{align}
    \text{Precision} &= \frac{TP}{TP + FP} \label{eq:precision} \\
    \text{Recall}    &= \frac{TP}{TP + FN} \label{eq:recall} \\
    F_1              &= 2 \cdot \frac{\text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}} \label{eq:f1}
\end{align}

Per-category precision, recall, and F\textsubscript{1}-score are computed separately for each cloud service category. Macro-averaged scores are obtained by averaging per-category scores with equal weight, so that all six categories contribute equally regardless of their frequency in the dataset. ROC curves and AUC are also computed per label, as well as for the micro and macro averages, providing a threshold-independent measure of discriminative ability.

\section{LLM-Based Disambiguation}

To test whether ambiguity can be mitigated by rewriting, an LLM-based disambiguation procedure was applied to the annotated dataset. The goal is to produce, for each ambiguous sentence, a version that preserves the original meaning while removing vagueness through the addition of concrete, measurable clarifications.

\subsection{Model and Prompting Strategy}

    The disambiguation uses GPT\textsubscript{5.4-mini} (OpenAI), accessed via the chat completions API with temperature set to 0 to maximise determinism and reproducibility. The model receives a detailed system prompt that specifies:

\begin{itemize}
    \item The task: for every row where the ambiguity flag is 1, rewrite the sentence into a new field; for rows where it is not, copy the original sentence verbatim with no changes.
    \item Core constraints: preserve the exact original meaning; only clarify ambiguity; add measurable values, technical specifics, or concrete constraints — preferably in parenthetical form.
    \item Allowed clarification patterns with realistic generic values (e.g., ``high speed'' $\rightarrow$ ``high speed (e.g., 100 MB/s throughput)''; ``secure'' $\rightarrow$ ``secure (e.g., AES-256 encryption at rest, TLS 1.3 in transit)'').
    \item Strict anti-laziness rules: no vague phrases, every rewritten sentence must include a concrete clarification, and varied but realistic values should be used across rows.
    \item Output format: valid CSV with two columns — \texttt{original} and \texttt{deambiguified\_description} — preserving row order and quoting every field.
\end{itemize}

The complete prompt is reproduced in Appendix~\ref{app:disambiguation_prompt}.

\subsection{Batch Processing and Validation}

The dataset is processed in chunks of 10 rows to keep each API call within context length limits while allowing the prompt to remain detailed. Each chunk is sent independently, and the returned CSV is validated before proceeding to the next chunk. Validation checks that: (i) the CSV is syntactically valid and contains exactly the two expected columns; (ii) the number of returned rows matches the number of input rows; and (iii) the original-text column preserves each input sentence exactly, in order. If any check fails, the chunk is retried up to three times with an auto-generated repair prompt that includes the validation error and the previous (invalid) output. After the first successful parse, an additional verification step compares the returned originals to the input originals; if they differ, a second repair cycle is triggered to fix the order or content.

Non-ambiguous sentences are retained verbatim. The result is a parallel dataset in which every row of the original corpus has a counterpart in the column \texttt{deambiguified\_description}, permitting side-by-side comparison.

\section{LLM as Direct Classifier}
\label{sec:llm-classifier}

Beyond rewriting, LLMs can perform classification directly through prompting, bypassing the BERT pipeline entirely. This configuration is evaluated to determine whether a general-purpose model, instructed in natural language, can approach or exceed the performance of the domain-specific fine-tuned classifier.

Two models from different generations are evaluated to assess whether advances in base model quality translate into better cloud requirement classification. Both are lightweight instruction-tuned models from the same product family, but GPT\textsubscript{5.4-mini} represents a more recent architecture and training pipeline. If the newer model substantially outperforms the older one, it suggests that ongoing model improvements will continue to raise classification accuracy; if they perform similarly, the task may already be near the limit of what general-purpose prompting can achieve, regardless of generation.

\begin{itemize}
    \item \textbf{GPT\textsubscript{4.1-mini}}: a lightweight, cost-efficient model from the earlier generation, serving as a baseline for cloud-requirement classification.
    \item \textbf{GPT\textsubscript{5.4-mini}}: a lightweight model from the subsequent generation, used for both disambiguation (Section~4.2) and direct classification.
\end{itemize}

All models are accessed via the OpenAI chat completions API with temperature set to 0, maximising determinism and reproducibility. No sampling or top-$p$ filtering is applied.

\subsection{Prompt Design}

The classification prompt contains three components: a system-level instruction, the six category definitions, and the batch of sentences to classify. The system instruction directs the model to output valid JSON only, with no explanatory text. The category definitions—drawn from the AI-CRAS ontology and identical to those presented in Section~2.1—are included inline in every user message:

\begin{quote}
\small
\textbf{Compute:} Processing resources: virtual machines, container orchestration, serverless computing, CPU/GPU and memory specifications.\\
\textbf{Data Handling:} Data storage and management: databases (SQL, NoSQL), storage systems, caching and data optimisation.\\
\textbf{Network:} Connectivity and traffic management: firewalls, load balancers, VPNs, DNS, latency and bandwidth specifications.\\
\textbf{Security \& Compliance:} Protection and regulatory adherence: encryption, identity management, certifications (ISO 27001, GDPR), access control.\\
\textbf{Management \& Monitoring:} Operational oversight: dashboards, logging, alerting, cost management, auditing.\\
\textbf{Cloud Service Essentials:} General cloud properties: elasticity, multitenancy, pay-per-use billing, availability zones, SLAs.
\end{quote}

Each sentence may receive zero, one, or multiple labels. A sentence that receives at least one label is classified as a requirement; otherwise, it is a non-requirement. The prompt instructs the model to output a JSON array with one object per sentence, where each object contains:

\begin{itemize}
    \item \texttt{id}: an integer matching the sentence's position in the batch;
    \item \texttt{labels}: a list of strings, each drawn from the six category names in their canonical form;
    \item \texttt{is\_requirement}: a boolean indicating whether the sentence describes a requirement.
\end{itemize}

\subsection{Zero-Shot Setting}

In the zero-shot setting, the model receives only the sentence batch and the category definitions—no labelled examples are provided. This configuration tests the model's ability to perform the classification task purely from its pre-trained knowledge of cloud computing terminology, without any task-specific fine-tuning or demonstration. The model must map each sentence to the six categories using only the one-line ontology descriptions supplied in the prompt, and must determine the binary requirement status from the label set.

Zero-shot classification is the most parameter-efficient setup: it requires no labelled data, no training infrastructure, and a single API call per batch. If an off-the-shelf LLM can approach BERT-level performance in this configuration, it would represent a significant practical advantage for domains where labelled datasets are scarce or expensive to produce. Conversely, a large performance gap would indicate that the domain-specific knowledge captured by the fine-tuned BERT is not trivially replicable through general-purpose pre-training alone.

The zero-shot configuration also serves as a clean lower bound for the LLM conditions: any improvement observed in the few-shot setting can be attributed entirely to the addition of in-context examples, isolating the contribution of demonstration-based learning from the model's intrinsic knowledge.

\subsection{Few-Shot Setting}

In the few-shot setting, the prompt is augmented with 16 labelled demonstrations that show the model how to perform the classification task by example. These demonstrations are drawn from the first 200 rows of the dataset, which are held out from evaluation entirely: no sentence the model sees during in-context learning is ever scored. The remaining 1,966 sentences form the classification set.

The 16 demonstrations are composed as follows. For each of the six categories, one ``prototype'' sentence is selected: a clean, unambiguous example that carries exactly that label and no others. An additional example per category is then added, chosen to reflect the natural label-count distribution observed in the dataset—roughly 75\% of labelled sentences carry a single label and 25\% carry multiple. The result is 12 labelled demonstrations (two per category) that expose the model to both pure and combined labels in realistic proportions. Finally, 4 non-requirement demonstrations—sentences carrying zero labels—are included to match their frequency in the pool (approximately one quarter of the data). All demonstrations are unambiguous, so the model learns from clear examples only.

The demonstrations are formatted as sentence–label pairs and prepended to the batch instruction using the same JSON output format as the zero-shot condition. The model is expected to generalise from these examples to unseen sentences.

The few-shot configuration tests whether in-context learning—a capability for which LLMs are specifically known~\cite{brown2020gpt3}—can compensate for the absence of supervised fine-tuning. Two outcomes are possible:

\begin{itemize}
    \item \textbf{Few-shot outperforms zero-shot:} this would indicate that the model benefits from concrete demonstrations beyond what the category definitions alone convey, and that in-context learning transfers effectively to the technical domain of cloud requirement classification.
    \item \textbf{Few-shot does not outperform zero-shot:} this would suggest that the category definitions are sufficiently informative on their own, or that the model's pre-training already provides adequate coverage of cloud-requirement language, leaving little room for demonstrations to add value.
\end{itemize}

\section{Experimental Design}
\label{sec:exp-design}

The classifiers are evaluated on a family of dataset subsets designed to isolate the effect of ambiguity and to measure the contribution of disambiguation.

\textbf{Baseline.} The full, case-insensitively deduplicated dataset comprising 2,166 sentences, containing both ambiguous (312) and non-ambiguous (1,854) examples. This reproduces the AI-CRAS configuration as faithfully as possible and serves as the reference against which all other conditions are compared.

\textbf{No-ambiguity subset.} A second subset excludes all sentences flagged as ambiguous by the \texttt{ambuiguity} indicator, leaving only the 1,854 unambiguous sentences. This tests whether training and evaluating exclusively on clear sentences improves performance.

\textbf{Deambiguified subset.} A third subset is derived from the LLM-rewritten dataset (Section~4.2). Every ambiguous sentence is replaced by its LLM-rewritten counterpart, while non-ambiguous sentences are kept unchanged. This tests whether disambiguation improves classification performance.

\textbf{LLM direct classification.} The two LLMs (GPT\textsubscript{4.1-mini}, GPT\textsubscript{5.4-mini}) are evaluated as standalone classifiers on the full 2,166-sentence dataset, in both zero-shot and few-shot configurations. No training or fine-tuning is performed; classification relies entirely on the prompt and, in the few-shot case, on in-context demonstrations drawn from a 200-row example pool disjoint from the evaluated set (1,966 sentences). Evaluation uses the same binary and per-category multi-label metrics as the BERT pipeline, excluding ROC-AUC.

\textbf{Per-category analysis.} Every experiment reports metrics not only globally but also broken down by the six cloud service categories. This per-category analysis is motivated by the finding in Chapter~3 that ambiguity rates vary substantially across categories (from 12.1\% for Security \& Compliance to 23.5\% for Cloud Service Essentials), and assesses whether ambiguity degrades performance uniformly or affects some categories disproportionately—and whether LLMs exhibit the same category-level variation as the fine-tuned BERT model.
