\chapter{Dataset and Annotation}

This chapter describes the datasets used in the experiments: the original AI-CRAS corpus, the ambiguity annotations added to it, and the LLM-deambiguified variants derived from it.

\section{The AI-CRAS Dataset}

The starting point for all experiments is the dataset introduced by Casalicchio and Cotumaccio \cite{casalicchio2024aicras}. It consists of 2,267 sentences extracted from publicly available Request for Proposal (RFP) documents related to cloud procurement, supplemented with examples generated via GPT-4 to increase coverage of the target domain. Each sentence was independently examined by two annotators and classified along two dimensions:

\begin{itemize}
    \item A binary label indicating whether the sentence constitutes a cloud requirement (\texttt{goal} = 1) or not (\texttt{goal} = 0). This is the label used for the binary classification task central to AI-CRAS; its distribution is shown in Figure~\ref{fig:goal_distribution}.
    \item A set of six one-hot encoded indicators assigning the sentence to one or more cloud service categories drawn from the AI-CRAS ontology: \texttt{compute}, \texttt{data\_handling}, \texttt{network}, \texttt{security\_compliance}, \texttt{management\_monitoring}, and \texttt{cloud\_service\_essentials}. These form the targets for the multi-label classification experiments.
\end{itemize}

Disagreements between the two annotators led to exclusion of the disputed sentence from the final dataset, preserving consistency. Figure~\ref{fig:category_counts} shows the number of positive labels for each cloud service category, and Table~\ref{tab:label_distribution} reports the exact figures.

\section{Ambiguity Taxonomy}

The ambiguity annotations follow the five-way taxonomy established in the requirements engineering literature by Berry and systematised by Bano \cite{bano2015ambiguity}. The five types, with representative examples drawn from the dataset, are:

\begin{description}
    \item[Lexical ambiguity] A word or phrase carries multiple meanings depending on context. \textit{Example:} ``The database server storage has to be provided on high speed disks (SSD's) for better performance'' — ``high speed'' and ``better performance'' are vague and admit multiple quantitative interpretations.
    \item[Syntactic ambiguity] The grammatical structure of a sentence admits more than one valid parse, leading to different readings. \textit{Example:} ``CSP / Bidder to conduct vulnerability assessment scanning of the Portal/Website for every 1 hour till the website is LIVE for rendering services'' — the attachment of ``for every 1 hour'' is ambiguous between modifying ``scanning'' and ``LIVE''.
    \item[Semantic ambiguity] The logical content can be interpreted in multiple ways even when the syntax is unambiguous. \textit{Example:} ``It is the prime responsibility of CSP to ensure continuity of service at all times of the Agreement including exit management period (may be one month)'' — the scope of ``at all times of the Agreement'' interacts ambiguously with ``exit management period''.
    \item[Language-error ambiguity] Grammatical mistakes or typographical errors that obscure the intended meaning. \textit{Example:} ``All the equipment's/Devices in the path have to be in HA mode'' — the apostrophe in ``equipment's'' and the undefined acronym ``HA'' introduce uncertainty about the intended specification.
    \item[Pragmatic ambiguity] The intended meaning relies on implicit contextual knowledge not present in the text. \textit{Example:} ``This will include system maintenance windows'' — without a definition of what constitutes a maintenance window, the requirement is underspecified.
\end{description}

\section{Annotation Procedure}

To support the experiments on ambiguity, the AI-CRAS dataset was enriched with two additional manually annotated columns:

\begin{itemize}
    \item \texttt{ambuiguity}: a binary indicator set to 1 if the sentence contains any form of ambiguity and 0 otherwise.
    \item \texttt{ambiguity\_type}: an integer encoding the specific ambiguity category, with values 1--5 corresponding to lexical, syntactic, semantic, language-error, and pragmatic ambiguity respectively. A value of 0 indicates no ambiguity.
\end{itemize}

All annotations were produced manually by examining each sentence against the taxonomy definitions above. The annotation was conducted in a single pass, with ambiguous sentences receiving exactly one type label corresponding to the dominant form of ambiguity present, even if multiple types could arguably coexist.

\section{LLM-Deambiguified Dataset}

A second dataset was generated by processing the annotated corpus through a large language model with the goal of rewriting ambiguous sentences into clearer, more concrete forms. The procedure, described in full in Chapter~4, used GPT\textsubscript{4o} with a structured prompt to produce a disambiguated version of each sentence. The output preserves the original row order and copies unambiguous sentences verbatim, yielding a parallel dataset in which every ambiguous sentence has a rewritten counterpart in the column \texttt{deambiguified\_description}. This dataset makes it possible to run the same BERT classifier on both the original and the disambiguated versions and directly compare performance.

Lexical ambiguity is by far the most common type, accounting for over four-fifths of all ambiguous sentences. This reflects the nature of RFP language, where vague qualitative terms (``high speed'', ``better performance'', ``adequate load balancers'') are routinely used without quantitative specification. Syntactic ambiguity is the rarest, which is consistent with the formal, template-driven style typical of procurement documents.

These per-category differences motivate the experimental design in Chapter~4, where classification performance is evaluated both globally and broken down by category.
